## Context

The M365 Excel "Create table row" action (`createTableRow`) makes one MS Graph API call per execution to append a row. When many executions hit the same file/table in a short window, this produces many slow, serialized Graph calls (the existing m365-excel queue already serializes per file with `group.concurrency: 1` plus a per-file rate limit). MS Graph's `POST /tables/:tableId/rows` endpoint already accepts **multiple rows in a single call** (`values: [[...row1...], [...row2...]]`), so we can collapse many same-table inserts into one request.

The plan introduces BullMQ-Pro **batch processing with group affinity**: a dedicated `m365-batch` queue receives only `createTableRow` jobs, a new batch worker fetches up to `batchSize` jobs from a single group at a time, and the action exposes a new `runBatch(jobs)` function that performs one multi-row Graph insert for the whole batch.

The batch worker sets `group.concurrency === batch.size` as a throughput cap. **Important correction:** this does *not* by itself guarantee "one in-flight batch per group." BullMQ-Pro group concurrency counts **jobs, not batches** (`increaseGroupConcurrency.lua` does `HINCRBY active:count +1` per job; `decreaseGroupConcurrency` runs per job in `moveBatchToFinished`). The "one batch per group" effect the docs describe holds **only when batches are full** — the docs' own "Partial batches" subsection admits batches come back smaller when a group has fewer than `size` jobs. Under trickle load (e.g. for-each fan-out, which enqueues with staggered `FOR_EACH_ITERATION_DELAY`), a partial first batch leaves free concurrency slots and a **second concurrent batch can start for the same group**. There is no config that gives "exactly one batch of up to N in flight" with bounded latency (`concurrency=1` collapses batch size to 1; `minSize=size` with no timeout risks indefinite starvation). Therefore serialization of same-file access is enforced by an explicit **per-file Redis lock** (Phase 6), not by group concurrency.

This is an intentional first cut. Failing batches are **all-or-none** (with retries kept, matching the existing single-row `createTableRow` contract — a Graph timeout-after-success can duplicate rows today too; batching only widens the per-incident blast radius). Moving `createTableRow` to its own queue removes the per-file `concurrency: 1` serialization it used to share with the other m365-excel actions; the **per-file Redis lock restores that cross-queue serialization** (see Phase 6 — `WorkbookSession` explicitly documents that it relies on per-file serialization being provided externally).

## Concurrency model: worker concurrency vs. group concurrency vs. batch size

Three distinct knobs on the batch worker (`make-action-batch-worker.ts`), each doing a different job. Getting them straight is what makes `group.concurrency: 10` safe — reviewers should read this before worrying about "10 concurrent writes":

- **Worker `concurrency` (3 for m365-excel, from `WORKER_CONCURRENCY`) counts BATCHES, not jobs.** Verified in `node_modules/@taskforcesh/bullmq-pro/dist/cjs/classes/worker-pro.js:102-143`: when batching, `nextJobFromJobData` wraps the whole fetched batch into a **single container job** (`id: jobIds.join(',')`, `name: 'batch'`, `data: ''`, then `.setBatch(jobs)`). That container occupies exactly one worker-concurrency slot. So `concurrency: 3` ⇒ at most **3 batches** processed in parallel. (Aside: this container's `data: ''` is the same fact behind the Phase 5 `worker.on('failed')` bug — the shared handler read an `undefined` executionId off the container.)
- **`batch: { size: 10, groupAffinity: true }`** — a batch is **always drawn from a single group** (`fileId::tableId::connectionId`); `groupAffinity` guarantees a batch never spans two files (and never mixes connections — the basis for one shared access check).
- **`group.concurrency: 10` (= `batch.size`)** is a per-group throughput cap that counts **JOBS, not batches**, and only ever manifests **within one file/group**. It must be ≥ `batch.size` or batches collapse to size 1 (same "counts jobs" trap as the `limiter.max` gotcha in Open questions).

Consequences (the reviewer takeaways):

| Scenario | Concurrent jobs in flight |
|---|---|
| All jobs from different files (1 job each) | ≤ 3 (worker concurrency), one file each. Each batch is size 1 — batching is a no-op here; nothing to coalesce. |
| One hot file, many jobs | ≤ 10 (group.concurrency), all same file → serialized at the write by the per-file lock |
| Worst case overall | `concurrency × batch.size` = 3 × 10 = **30 jobs**, but spanning **at most 3 distinct files** (≤10 same-file jobs each) |

- **"10 different files ⇒ 10 concurrent jobs" is false.** Different files are different groups, so they land in separate size-1 batches, capped at worker concurrency (3). The 10 never aggregates across files.
- **Cross-file concurrency is SAFE and DESIRED.** Different files have independent `WorkbookSession`s and (Phase 6) independent lock keys (`<tenant>:<fileId>`), so concurrent writes to different files never conflict. That parallelism is exactly what moving `createTableRow` off `group.concurrency: 1` buys. The only dangerous concurrency is **same-file**, which is bounded by `group.concurrency` and serialized by the per-file Redis lock.
- **Multi-process is why the lock must be distributed.** Each worker process has its own `concurrency: 3`, so the fleet runs `3 × numPods` concurrent batches → that many distinct files at once (still safe). Same-file serialization holds across processes **only** because the lock lives in Redis — a local/in-process concurrency setting cannot provide cross-process serialization, which is the decisive reason `group.concurrency: 1` cannot be reused on the batch path and a distributed lock is required.

## Goals

- A new `m365-batch` BullMQ-Pro queue that receives **only** `createTableRow` jobs.
- A new batch worker (`make-action-batch-worker.ts`) that processes jobs in batches using `batch.groupAffinity: true` and `group.concurrency === batch.size` as a throughput cap (NOT relied on for write serialization — see Phase 6).
- A **per-file Redis lock** that serializes all `WorkbookSession` reads/writes to the same file across both the m365-excel and m365-batch queues, restoring the invariant `WorkbookSession` depends on.
- `createTableRow` exposes `runBatch(jobs: Array<{ $: IGlobalVariable }>)` that performs a **single** multi-row Graph insert per batch and sets each job's own action output (`sheetRowNumber`).
- `run($)` is preserved for test runs and delegates to `runBatch([{ $ }])` to avoid duplicated logic.
- Per-job correctness preserved: each job records its own execution step and enqueues its own next step on success.
- All-or-none failure: if the batch fails, every job in the batch is marked failed; BullMQ retries the whole batch per the configured attempts.
- Batch size is configurable; a per-file/queue rate limit is retained on the batch queue.

## Non-goals

- ~~Partial-batch success / per-job failure isolation (explicitly all-or-none for now).~~ **Superseded by Phase 7** — **pre-write** per-job failure isolation (bad params / deleted step / denied access / **un-buildable row**) is now in scope. The 2026-06-20 rework added **per-job row-build isolation**: a job whose `columnValues` reference a column that doesn't exist in the table is excluded (`failed`) at row-build time — before the POST — while siblings commit (this is build-time isolation, not the poison-pill fallback below). Still out of scope: (a) **post-write bookkeeping isolation** — a job whose post-commit step-record/next-step/advance throws still stalls (catch-log-continue), not `setAsFailed` (deferred follow-up, see Open questions); (b) **write-level / poison-pill isolation** — the multi-row Graph **POST itself** stays atomic all-or-none; we do **not** fall back to per-row inserts to isolate a row the server rejects *during* the write (only rows that fail to build *before* the write are isolated).
- Relying on BullMQ group concurrency for write serialization (it can't guarantee one batch per group — see Context). Serialization is the per-file Redis lock's job instead.
- Batching any action other than `createTableRow`.
- Using the MS Graph `$batch` multiplexing endpoint (we use the native multi-row `values` array of a single `POST /rows`).
- Deduplication of rows across retries (see Edge cases — a retried batch may re-insert if the original POST partially applied).

## Decisions made

- **Grouping granularity:** Group by **`fileId` + `tableId`** (the queue group id is `"<fileId>::<tableId>"`). Chosen over fileId-only (which would force runBatch to sub-partition by table and issue multiple POSTs) because group affinity then guarantees every job in a batch targets the same table → exactly one multi-row POST per batch. **Trade-off captured as a risk:** two different tables in the same file can now be written concurrently through separate `WorkbookSession`s; previously per-file `concurrency: 1` serialized them. See Edge cases.
- **Routing to the batch queue:** The **action declares its own target queue** (a `batch` config on the action definition) rather than hard-coding `stepKey === 'createTableRow'` in `enqueueActionJob`. More generic/reusable for future batchable actions, and keeps batch knowledge with the action.
- **Failure handling (first cut):** **Whole batch fails together.** `runBatch` throwing → every job marked failed via the shared failure helper, no next steps enqueued, BullMQ retries the whole batch per `attempts`. Chosen over per-job isolation for simplicity and because the single multi-row POST is effectively atomic at the API level. (Phase 7 layers **pre-write** per-job isolation on top of this without changing the write's all-or-none behavior — see below.)
- **Partial failure scope (Phase 7):** Chose **pre-write per-job isolation only** over (a) also isolating post-write bookkeeping failures and (b) write-level poison-pill isolation. Rationale: a job that fails *before* the write (bad params, deleted step, denied file access, un-buildable row) can be cleanly excluded from the atomic POST and `setAsFailed` on the resolve path, so one bad job no longer sinks healthy siblings. (The file-access security fix is handled at the grouping layer — connection-pinned group key + one shared check — rather than as a per-job check; see the 2026-06-20 deviation.) Post-write bookkeeping isolation is deferred (the catch-log-continue rule is already duplicate-safe). Write-level poison-pill isolation (a row the **server** rejects mid-POST) was rejected for the first cut because per-row attribution/fallback materially changes the atomic-write contract and adds a per-row retry strategy — note this is distinct from the build-time row isolation that shipped (bad column name), which happens before the POST. For-each keeps today's semantics (any failed iteration → execution failure) over partial-success aggregation, to avoid new `processForEachStatus` semantics.
- **`setAsFailed` mechanics (Phase 7 invariants, verified in bullmq-pro 7.44.0):** Per-job isolation rides the **resolve** path, never a throw. Three hard constraints: (1) `setAsFailed` members emit **no `failed` event** (`moveBatchToCompleted` → `job.moveToFailed` directly; the container emits `completed`), so the batch processor must run their failure side-effects **inline** via a shared helper, not via the `worker.on('failed')` fan-out; (2) the `setAsFailed` error **must be `UnrecoverableError`** or a retriable re-batch would re-run `runBatch` → duplicate rows; (3) a processor **throw overrides `setAsFailed`** (`moveBatchToFailed` fails all members with the thrown error), so the write-failure path must stay all-or-none throw and must not mix inline `setAsFailed` side-effects.
- **Batch size & rate limit:** Configurable batch size (default 10), `group.concurrency = batch.size`, **retain** a per-file/queue rate limit on the batch queue so we don't hammer Graph between batches.
- **run vs runBatch:** Keep `run($)` (test runs still call it; test runs execute synchronously via `testStep`, never through the queue). `run($)` runs the test-run-only rate-limit guard, then delegates to `runBatch([{ $ }])` so insert logic lives in one place.
- **Worker code reuse (targeted helpers, not a rigid split):** `processAction`'s halves aren't cleanly separable (in-place `metadata` mutation, `PartialStepError` flip, `start-for-each` side-effect in nextStep resolution), so instead of a monolithic `prepareAction`/`finalizeAction` pair we extract four small helpers (Phase 2: **A** prepare, **B** record-step, **C** resolve-next, **D** worker advance) reused by both paths. `processAction = A → run → B → C`; single-job worker `= processAction + D`; batch worker `= A×N → runBatch → (B+C+D)×N`. Chosen over the rigid split because each helper is small/testable and the batch path only needs the simple branches (`createTableRow` never throws `PartialStepError` nor returns `start-for-each`/`jump-to-step`/`pause-execution`).
- **Retries on failed batches:** **Keep retries** (don't drop to `attempts: 1`), matching the existing single-row `createTableRow` behavior. Chosen over no-retry because the common retriable cases (429/503) fail *before* server-side mutation and don't duplicate; dropping retries would regress reliability for those. The genuinely dangerous case — a client-side timeout *after* Graph applied the rows — is a pre-existing accepted risk for single-row inserts (`ETIMEDOUT` is in `RETRIABLE_ERROR_SUBSTRINGS`); batching widens blast radius from 1 row to ≤ `batchSize` rows but doesn't change the trade-off. A future idempotency mechanism (stamp each row with `executionId`, check-before-insert) is the real fix if duplicates become a problem.
- **Write serialization via per-file Redis lock (not group concurrency):** Verified against the bullmq-pro Lua and docs that `group.concurrency = batch.size` only serializes *full* batches; partial batches (the common case under trickle load) allow two concurrent batches per group. Since `WorkbookSession` documents that it relies on per-file serialization being supplied externally (it shares a session ID in Redis "no synchronization needed"), and the original per-file `concurrency:1` existed for exactly this reason, correctness must not depend on bullmq batch semantics. Chosen: an explicit **per-file distributed lock** (built on the existing `redisAppDataClient`, `SET … NX PX` + Lua compare-and-delete release) wrapping all `WorkbookSession` usage across both queues. Alternatives rejected: (a) `minSize = size` + no timeout (indefinite starvation for lone executions); (b) accepting concurrent appends (unsafe — shared workbook session, and `sheetRowNumber` accuracy depends on no interleaving).
- **Lock contention behavior (Option C: tiny retry, then re-queue):** When a worker picks up a job whose file is already locked, it does a **short up-front retry** (~2–3 attempts over ~100–300ms, jittered) to absorb micro-contention, then **re-queues** rather than blocking: `worker.rateLimitGroup(job, delayMs)` + `WorkerPro.RateLimitError()` (the existing idiom in `handle-failed-step-and-throw.ts:58–68`, which does **not** consume an attempt and *pauses* the group rather than hot-looping). Chosen over blocking-wait (Option A) because m365 ops are slow — a blocked worker/batch slot would stall and starve other files. Because no attempt is burned and the lock holder always completes/releases (TTL covers worker death), the contender always makes progress; worst case is added latency. **Critical (placement):** the lock is acquired **after prepare (which yields the `fileId`) but before any execution-step insert**, and contention short-circuits **without** `finalizeAction` — so contention never writes a spurious `'failure'` step. For the single-job path this means **inside `processAction`** (between its internal prepare and `run`), NOT in the worker processor — because `testStep` → `processAction` is the only path a test run takes, so putting it in the worker would leave test-run writes unlocked. For the batch path it lives in the batch worker (no test runs there).
- **Lock follows `WorkbookSession` usage, and test runs are included:** the lock guards stateful/mutating session ops, not action type. **Dynamic data stays lock-free** (read-only metadata, opens no session — see list-tables/index.ts:33–35). **Test-run `createTableRow` acquires the lock** because it writes with a session — primarily to protect concurrent production batches: an unsynchronized test-run write sharing a file's session with a live batch can trigger a Graph session conflict on the batch → batch retry → re-POST → the Q1 duplicate-rows risk. Contention handling is kept simple and keyed off the `testRun` flag: **same** tiny up-front retry as the worker, but on give-up the test-run path throws a user-facing `StepError` ("file busy, try again") instead of `FileLockContentionError`/re-queue (there is no `job`/`worker` to re-queue to). No separate long-blocking-wait strategy.

### Phase 7: Per-job failure isolation (partial batches) — additive follow-up

> **Reworked 2026-06-20 (commit `cff17c60`).** The checkboxes below record Phase 7 as first implemented (a `validateBatchJob?` hook + `prepareAndValidateActionJob` doing the per-job validation in the worker, with grouping by `fileId::tableId` and per-job `validateCanAccessFile`). The shipped design folds per-job validation **into `runBatch`** (which now returns `RunBatchJobResult[]`), pins `connectionId` into the group key, and uses **one shared access check**. The worker-level isolation mechanics (split prepare, `setAsFailed` on the resolve path, write-failure all-or-none throw, failed-first ordering, shared `handleFailedJob`) are unchanged. See the 2026-06-20 deviation for the full diff of intent.

Rationale: the first cut (Phases 1–6) is strictly **all-or-none** — one bad job (invalid params, deleted step, a user whose file access was revoked) fails the entire batch and takes healthy siblings down with it; for prepare failures it does so with a non-retriable `UnrecoverableError`, so the healthy jobs don't even retry. This phase isolates **pre-write** per-job failures: a job that fails *before* the multi-row write is marked failed on its own (`JobPro.setAsFailed`) and excluded from the write, while the healthy jobs commit and complete normally. The atomic multi-row write itself is unchanged (still all-or-none). **This phase closes the file-access security open question** — after the rework, by connection-pinned grouping + one shared `validateCanAccessFile` (not a per-job check) — making that slice a ship-blocker on the same tier as Phase 6.

**Hard constraints — verified in the bullmq-pro 7.44.0 source; violating any of these reintroduces duplicate rows or silently-stuck executions:**
- **`setAsFailed` emits no `failed` event.** On a resolving processor, `JobPro.moveBatchToCompleted` (`dist/cjs/classes/job-pro.js:96-106`) moves `setAsFailed` members to the failed set via `job.moveToFailed(...)` *directly*; event emission only happens in the base `Worker.processJob` loop (`bullmq/dist/cjs/classes/worker.js:606-607` completed / `638-639` failed), which fires **`completed`** for the batch *container*. So the Phase 5 `worker.on('failed')` fan-out does **not** run for partial-failed jobs — the batch processor must perform their failure side-effects **inline**.
- **The `setAsFailed` error MUST be `UnrecoverableError`** (or `.name === 'UnrecoverableError'`). A retriable error would let the job re-enter a future batch and re-run `runBatch` → duplicate rows.
- **Throwing overrides `setAsFailed`.** A processor throw routes through `moveBatchToFailed` (`job-pro.js:147-156`), which fails *every* member with the thrown error (ignoring per-job `failedError`) and retries the whole batch. So per-job isolation only takes effect on the **resolve** path; the write-failure path must remain all-or-none throw and must not mix inline `setAsFailed` side-effects in the same invocation.

## Edge cases considered

- **Mixed tables / mixed identities in one batch:** Prevented by `group.affinity` + group id `fileId::tableId::connectionId`. `runBatch` still asserts defensively — a single `(fileId, tableId)` **and** a single access identity (pipe-owner email + connectionId + the auth data the access verdict is computed from: tenantKey + Plumber folderId) across the parsed jobs — and throws if violated, since the whole batch is written through one session after one access check.
- **A batch mixes different executions/flows/steps (only `fileId`+`tableId` is shared):** two different `createTableRow` steps in different flows pointing at the same file+table share a group → batched together. So all per-job work (prepare, record-step, resolve-next, advance) is strictly per-job — no batch-wide execution/step assumptions — and `runBatch` builds each row from **that job's own** `columnValues` against the shared (read-once) table header. A `createTableRow` inside a for-each is the same shape (each iteration = its own job, same group) and a prime batching case; per-job for-each metadata (`getForEachMetadata`/`patchIterationStatus`/`processForEachStatus`) is preserved via helpers B/D.
- **Concurrent same-file access (cross-queue + partial batches):** Two tables in one file (per-table grouping), a batch vs. a non-batch action, or two overlapping partial batches could otherwise hit the same workbook session concurrently. **Mitigated by the Phase 6 per-file Redis lock**, which serializes all `WorkbookSession` use per `fileId` across both queues — restoring the invariant `WorkbookSession` documents it relies on.
- **Lock-related cases:** worker death while holding the lock → TTL auto-expiry prevents permanent deadlock; operation longer than TTL → renew or size TTL up; lock contention → short jittered up-front retry, then re-queue via `rateLimitGroup` + `RateLimitError` (group paused, **no attempt consumed**, **no failed execution step** because the lock is taken before the insert); repeated contention can't exhaust `attempts` and the holder always releases, so the contender always makes progress (added latency only, no live-lock).
- **Multi-row response index:** Graph returns a single `workbookTableRow` with one `index` and does not document whether it's the first or last of the added rows. Approach A assumes *first*; Phase 1's ≥2-row test is the hard gate. Rows are guaranteed contiguous/unshifted by the Phase 6 lock (no concurrent appends). Fallback B (pre-read row count under the lock) is index-semantics-independent if A fails. Note: the documented endpoint is `/rows/add`; current code posts to `/rows` — both are valid Graph aliases.
- **Batch of size 1:** `runBatch` handles it; this is exactly the `run($)` delegation path used by test runs.
- **Test runs:** Never batched — `testStep` calls `processAction` synchronously which calls `run($)`. The test-run-only rate-limit guard stays in `run`. Test-run `createTableRow` still acquires the per-file lock (it writes with a session), but on contention throws a user-facing `StepError` rather than re-queuing (no worker/job exists). Read-only **dynamic data** opens no session and is exempt from the lock.
- **Prepare failure for one job (bad params, deleted step, missing fileId):** First cut — all-or-none, the whole batch fails. **Phase 7** changes this on the write-success path: the one bad job is `setAsFailed(UnrecoverableError)` + handled inline and excluded from the write; healthy siblings commit. `getGroupConfigForJob` already throws at enqueue time when `fileId` is missing (existing pattern), keeping those malformed jobs out of the batch queue entirely.
- **(Phase 7) Partial failure rides the resolve path only:** if the write itself fails, isolation does **not** apply — a throw fails the whole batch (bullmq `moveBatchToFailed` ignores per-job `setAsFailed`), so write failures stay all-or-none and the bad pre-write jobs re-prepare-fail on retry (usually as size-1 batches that then resolve and isolate). The processor must never combine inline `setAsFailed` side-effects with a throw in one invocation.
- **(Phase 7) No `failed` event for isolated jobs:** `setAsFailed` members never emit `failed`, so their `Execution.setStatus`/error-email/iteration-patch side-effects are done inline by the processor (shared `handleFailedJob` + B-failure + D-iteration-patch), not by the `worker.on('failed')` fan-out. For-each siblings that succeed still record `success` and advance; the failed iteration patches its slot to `'failure'` and the execution is marked failure (matches single-job today).
- **(Phase 7) All jobs fail pre-write:** healthy set empty → no Graph POST at all → resolve with every job `setAsFailed`. (Indistinguishable downstream from the old all-or-none prepare failure, minus the wasted POST.)
- **Retry duplication:** A retried batch re-issues the multi-row POST. If the original POST partially applied before failing (unlikely for a single call), retry may duplicate rows. Accepted for now; noted as a non-goal (no dedup).
- **Next-step metadata / for-each:** Each job's `finalizeAction` computes its own `nextStep`/`nextStepMetadata`, mirroring the single-job worker.
